# AI 协同记录 · 说明

> 这份目录回答评委两个问题：**这堆代码是不是 AI 一把梭出来的？** **人在这中间到底做了什么？**

## 一、这是什么

比赛要求「导出与 AI 的对话历史，须包含至少 3 个核心功能迭代的完整 Prompt 链」。
本目录就是这个导出的**整理版**，不是截图拼贴，也不是事后重写的回忆：

| 文件 | 内容 |
|---|---|
| `00-说明.md` | 你正在读的这一份：导出方法、阅读顺序、诚实声明 |
| `01-室内偏好.md` | 链 A：「不想去室内」听不懂 → 三态改造 + 地点库 49→200 |
| `02-预算语义.md` | 链 B：预算被当成「单站上限」→ 日预算 + 数据错标清洗 |
| `03-前端风格.md` | 链 C：整站换风格，8 轮推翻重来 |
| `raw/conversation.md` | **原始对话全文**（177 条消息，25 万字符，未删改内容） |
| `raw/conversation.jsonl` | 同一份内容的机器可读版（便于 grep 校验） |

三条链合计覆盖了 11 月 11 日 22:22 到 11 月 13 日 17:11 的连续三次迭代，
每一次都从「我发现这里不对」开始，到「提交 + CI 绿」结束。

## 二、导出方法（可验证，不是口头声明）

对话来自 DeepSeek Harness 的本地会话文件
（`~/.dsh/sessions/--D-bisai--/session-*/session.v4.jsonl.zstd`，zstd 压缩的 JSONL）。
导出脚本做了三件事：

1. 解压全部会话（根会话 12 613 行 / 7.9 MB，另有 3 个 fork 会话）；
2. 只保留 `user/message` 的正文与 `assistant/message` 的正文，**丢掉**工具调用明细、
   图片、以及系统注入的运行时上下文（`Current runtime context` 之类）；
3. 按时间排序、按前 80 字去重（fork 会话会重复同一批消息）。

因此 `raw/conversation.md` 里的每一段都能和会话文件逐条对上。
消息条数：**177 条，其中 80 条是我说的话**——这个比例本身就是证据：
这 4 天里我发了 80 条指令，AI 回了 97 条，中间还有 1 666 次工具调用。

## 三、怎么读这三条链

每条链结构固定：

1. **起点**：我发现的现象（原话，带时间戳）
2. **Prompt 链**：我每一句问了什么、AI 当时是怎么答的、我为什么这么追问
3. **转折**：AI 哪一步判断是错的 / 不完整的，我怎么把它掰回来
4. **落地**：改了哪些文件、什么提交、用什么命令验证、输出是什么

**重点看第 3 节。** 三条链里 AI 都犯过错：

- 链 A：AI 一开始想直接给解析器加词表（治标），被我追问「为什么所有人都说了还是不行」之后，
  才挖出「`require_indoor` 是布尔值，`False` 等于没提」这个真正的病根；
- 链 B：AI 自己写的预算代码把「日预算」理解成「每站上限」，
  是**我按计算器发现 98+60+60≠150** 才被翻出来的；
- 链 C：AI 连做 5 套移动端风格，我一句「我不想要这样的一长条」全部作废。

这三段是「人怎么控制 AI」最直接的证据：**不是让它自由发挥，而是给它可验证的失败。**

## 四、我的意图控制策略（三条，贯穿全程）

1. **先说清楚「不要做什么」**。80 条指令里有 23 条是「先别动手 / 先分析 / 先设想 / 先别 push」。
   我不让 AI 一边诊断一边改代码——它一旦同时做这两件事，就会把现象当成原因。
2. **一次只改一件事，改完必须能验证**。每条链结束时都有可执行命令 + 明确的期望输出
   （`pytest` 数字、接口返回、截图）。AI 说「修好了」不算完，我要看 127 passed 和 200 条数据。
3. **让它报数字，不要让它报形容词**。「好多了 / 更合理了」一律打回去，
   要的是「室外 23→78」「海岸城 0 条→3 条」「方案合计 98/150 元」这种能在页面上看见的东西。

## 五、诚实声明

- **代码主要由 AI 生成**，我负责定范围、定优先级、验收和挑错。这一点不掩饰。
- 但**每一个需求、每一次否决、每一个验收标准都来自我**：只做深圳、不做小程序、
  不要黑按钮、不要一长条、预算必须按一整天算、书城没有门票——这些话在对话里都能查到。
- 时间戳是本地时间（Asia/Shanghai），来自会话文件原始 `time` 字段。
- 对话里出现过的问题（推送失败、隧道不通、虚拟环境权限坏掉）都是真实发生过的，
  没有为了好看而删掉。**翻车记录本身就是工程能力的一部分。**

## 六、顺带说明：为什么有 46 个提交

比赛禁止「一次 initial commit 提交全部功能」，所以开发过程中每次落地都单独提交，
提交信息写的是一句话的因果（例如 `feat: 到点别关门，也别把「海岸城到龙华」算成 40 分钟`），
不是 `update` / `fix bug`。提交时间分布在 4 天里，与这 80 条指令基本一一对应。
