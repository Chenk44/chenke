# 数据说明

`data/pois_shenzhen.csv` 是这个项目最核心的资产。

算法可以复现，框架可以照抄，但"**另外 9 个字段怎么标**"这件事没法照抄——
它决定了推荐结果是不是"真的很懂一群人出去玩"。

## 1. 规模

| 项 | 数值 |
| --- | --- |
| 地点数 | 202（20 列，其中 `open_hour` / `close_hour` 是后加的） |
| 商圈 | 20 个（海岸城、高新园、少年宫、大鹏、后海、海上世界、华侨城、车公庙、万象城、宝安中心、南头、购物公园、莲花、仙湖、东门、大梅沙、盐田、市民中心、福田中心、龙华） |
| 品类 | 7 类：公园 58、玩乐 38、展览 34、影院 22、餐饮 22、咖啡 18、夜生活 10 |
| 室内地点 | 122 / 202（室外 80，每个商圈至少 3 个室外选项） |
| 营业时间 | 168 / 202 有明确营业区间（149 条来自高德，其余 19 条按品类兜底但仍有区间；其余 34 条按「全天」处理） |
| 商圈通行时间 | `data/area_travel.csv` 380 行（20 商圈 190 对 × 驾车/公交） |
| 覆盖范围 | 从宝安中心到大鹏、盐田，横跨深圳东西两端 |

**为什么是 202 条而不是 5 000 条**：500 条从大众点评抄来的数据，字段只有"名字 + 评分 + 人均"，
而这 202 条每一条都有 9 个人工标注字段。**在"一群人决策"这个场景里，后者比前者有用得多。**

**这 202 条是怎么来的**（三步，都可以复现）：

1. `scripts/fetch_amap.py` 用高德 `place/text` 按 14 个关键词 × 20 个商圈拉回 1 685 条候选，
   再 `scripts/shortlist.py` 品牌去重、每商圈每品类限额，得到 647 条短名单。
2. `scripts/draft_labels.py` 按规则给短名单里每条记录先猜一版 9 个高德拿不到的字段
   （草稿），人工复核后再 `scripts/merge_pois.py` 与最早那 49 条人工数据合并——
   同名且 800 米内视为同一个地点，**人工数据优先**。
3. `scripts/backfill_hours.py` 从短名单的高德 `open_time` 回填营业时间（149 条命中），
   认不出时间串的按品类兜底（公园全天、美术馆 10-22、夜宵摊到凌晨 2 点）。

也就是说：**名字、坐标、评分、人均来自高德；室内外、安静度、人数上下限、带娃、预约、
排队、标签、一句话理由是我们自己标的。**

## 2. 字段定义

| 字段 | 类型 | 说明 | 来源 |
| --- | --- | --- | --- |
| `id` | str | 稳定主键，方案和投票都引用它 | 自建 |
| `name` | str | 展示名 | 高德 POI |
| `area` | str | 商圈（不是行政区），深圳人按商圈活动 | 人工 |
| `district` | str | 行政区 | 高德 POI |
| `category` | enum | 玩乐 / 公园 / 展览 / 餐饮 / 咖啡 / 夜生活 / 影院 | 人工归一 |
| `lat` / `lng` | float | 火星坐标系（GCJ-02），和高德一致 | 高德 POI |
| `avg_price` | float | 人均消费（元） | 高德 POI + 人工修正 |
| `rating` | float | 平台评分，用于基础质量分 | 高德 POI |
| `indoor` | bool | **是否全程有遮蔽**（下雨能不能去） | 人工 |
| `quiet` | float 0~1 | **2 人对话时，需不需要提高音量**。0.1 得喊，0.9 图书馆级 | 人工 |
| `min_people` / `max_people` | int | 能舒服容纳的人数区间（包间起订、场地容量） | 人工 |
| `kid_friendly` | bool | 推婴儿车能不能进，有没有儿童设施 | 人工 |
| `need_booking` | bool | 周末不预约会不会白跑 | 人工 |
| `queue` | float 0~1 | **周六下午 3 点**的排队程度，0 随到随进，0.9 一小时起 | 人工 |
| `tags` | str | `\|` 分隔，用于忌口匹配（辣 / 海鲜 / 火锅 / 素食 / 咖啡 / 拍照 …） | 人工 |
| `blurb` | str | **一句话决策理由**，不是形容词 | 人工 |
| `open_hour` / `close_hour` | float | 营业区间，24 小时制；跨零点写成 26.0（= 次日 2 点） | 高德 `open_time` + 品类兜底 |

### 标注标准（写给未来的自己）

这三条决定了数据质量，也决定了答辩时能不能自圆其说：

1. `quiet` 统一按"**2 人对话的轻松程度**"标，不按"整体氛围"。所以热闹的火锅店
   是 0.15，而同样热闹但桌子间距大的海鲜大排档是 0.35——后者能聊天。
2. `queue` 统一按"**周六下午 3 点**"标。所有记录锚在同一个时间点，
   否则"要排队"三个字在不同人心里是不同量级。
3. `blurb` 必须包含**决策信息**，不能是"环境优雅，值得一去"这种。合格的样子：
   - `"6 人以上要提前一天订包间，5 人以下别来"`
   - `"下午三点后排队 40 分钟，开门就去"`
   - `"展厅里要小声，不适合想聊天的一群人"`

   → 每一条都回答了"我们这群人该不该选它"。这是这套数据和点评标签最本质的区别：
   **点评的标签是给"陌生人"看的，我们标的是"一群人决策需要知道的东西"。**

## 3. 数据从哪来（合规声明）

- **结构化字段（名称、坐标、品类、人均、评分）来自高德开放平台 POI 检索接口。**
  通过官方 Web 服务 API 获取，遵守其服务条款，不爬取网页、不绕过任何反爬机制。
- **其余字段为人工标注**，依据公开的商户信息、场地照片和实地/以往经历，
  不包含任何平台的用户评论原文。
- **没有爬取大众点评或小红书。** 原因是三点，按重要性排序：
  1. **合规风险不可控**：两个平台的用户协议都明确禁止抓取，参赛作品不该带这个风险；
  2. **稳定性不可控**：反爬策略以周为单位变化，10 天工期里押注爬虫是工程上的自杀；
  3. **最关键的——数据本身不对**：陌生人的评分回答的是"这个地方好不好"，
     而我们回答的是"**我们这群人**去了会不会开心"。这两个问题的答案经常相反：
     一家排队一小时的网红店点评 4.8 分，但对"带娃 + 只想聊两小时"的五个人来说是灾难。

  第 3 点是产品设计的一部分，不是借口：所以我们做了**事后评价**功能
  （`POST /api/reviews`），让这个局的数据在玩完之后沉淀成"自己人的口味"，
  比任何平台的陌生人评分都更贴近"下次我们该去哪"。

## 4. 更新与校验

```bash
# 幂等：已存在的地点更新，不存在的新增
python -m scripts.seed

# 清空重建（改表结构后用）
python -m scripts.seed --reset
```

加载时会做**启动即校验**（`algo/loader.py`），任何一条脏数据都会让启动直接失败：

- 必填字段缺失、经纬度超出深圳范围、评分不在 0~5、人均为负；
- `category` 不在 7 个枚举值内；
- `min_people > max_people`；
- `open_hour` / `close_hour` 不在合理区间（要求 `0 ≤ open < 24`、`open < close ≤ 26`）。

**交叉体检**（`scripts/audit_pois.py`）负责抓"能过校验但明显不合理"的标注：

```bash
python -m scripts.audit_pois          # 打印报告
python -m scripts.audit_pois --csv    # 另外写成 .tmp/audit.csv
```

它检查七件事：公园被标成室内、名字像户外却标室内（反之亦然）、餐饮/咖啡人均为 0、
人均 > 800、评分 < 3.5、营业区间不足 2 小时或 22 点后才开门、标签/一句话理由为空，
以及商圈层面的「室外点不足 3 个」和同名同坐标的重复行。当前 **0 处可疑**。

> 这一轮体检真的抓出过 16 处误判——全是「陈记山水客家菜」「金光华广场」这类
> 名字里带「山」「广场」的门店被判成户外。词表收紧后重新回填营业时间，才归零。

> 设计意图：**脏数据必须在启动阶段炸掉，而不是上线后算出离谱结果。**
> 这条也有测试（`test_loader_rejects_unknown_category`）。

## 5. 还能怎么扩（下一步计划）

1. 再补 100 条：目标是每个商圈的**室外点位 ≥ 5**（现在 20 个商圈都已 ≥ 3，
   最薄弱的购物公园 3 个、盐田 4 个；再往上就要靠人工去填高德查不到的小公园）；
2. 高德路径规划已经预计算完 190 对商圈（`data/area_travel.csv`），下一步是补
   「地点 → 商圈中心」的距离，让起点段也不用估算；
3. 营业时间现在是「一天一个区间」，没区分工作日/周末、也没接临时闭馆，
   要精确到"今天开不开"得接高德的营业状态或人工维护节假日表；
4. 扩量后 `pool_size` 保持 24，组合搜索量不变（`C(24,3)`），只是候选质量更高；
5. 新增字段前先加测试，再改 loader，最后才改数据——顺序反了会浪费半天。
