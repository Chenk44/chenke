02问题是真的，不是编的

「去哪玩」这件事，一个人用不着软件；五个人就开始互相谦让，最后去了楼下的商场。

真实场景

周五晚上群里问「周六去哪」，五个人各自发链接，没人拍板。四十分钟后有人说「要不就海岸城吧」——不是最合适的，是最不用吵的。

现有工具的缺口：大众点评回答「这家店好不好」，小红书回答「哪里好看」，没有一个回答「我们这群人该去哪」。

为什么现有推荐系统解决不了

单用户推荐是「猜你喜欢」；群体决策是「谁让步」。前者最大化一个人的分数，后者要在「平均都还行」和「没有人特别难受」之间做取舍。

我们用 0.6×平均 + 0.4×最低 来量化这件事：平均分高但有人很难受的方案，不该排第一。

维度大众点评 / 小红书通用的「AI 推荐」尘客
输入你的位置 + 历史行为一句话每个人自己的三个滑杆 + 硬条件 + 一句话
输出一个地点一段文字一条动线：几点到哪、贵不贵、下雨去不去得
多人不支持把多个人的话拼进 prompt逐人打分 → 聚合 → 明确告诉你谁让步了
可解释评分和评论「因为大家都喜欢」每个方案给出共识分、最低分、绕路时长、打烊提示
这一节没有数字，因为痛点不是量出来的。但下一节全是数字 —— 痛点靠讲，能力靠算。

03数据是我们自己标的，不是爬的

高德能给名字、坐标、评分、人均、营业时间；给不了「这地方安静吗」「适合几个人」「下雨能不能去」。

高德开放平台给的（合法 API）

name · location · typecode · adname · address · tel · rating · cost · open_time · business_area

共 20 列 中占 11 列，来源可查、可复现（scripts/fetch_amap.py）。

我们自己标的 9 个字段

室内/室外 · 安静度 · 人数上下限 · 是否适合带娃 · 是否要预约 · 排队程度 · 标签 · 一句话理由 · 商圈归属

这 9 列是「一群人决策」真正需要的，也是这个项目最花时间的地方。

04算法上有三处硬东西

都能在代码里逐行找到，也都有单元测试钉住。

① 单人效用 → 群体共识

U(p, m) = 0.30·距离 + 0.20·价格 + 0.20·评分 + 0.18·安静度 + 0.06·排队 + 0.06·带娃 − 硬约束降权 每个人的滑杆只改自己的权重；口味（忌口、想待室内、带娃、开车）是乘 0.2 的强惩罚而不是直接过滤 —— 因为「一个人不吃辣」不该让全组失去火锅这个选项。
consensus = 0.6 × mean(U) + 0.4 × min(U) − 绕路扣分 − 超时长扣分 − 打烊扣分 0.4 的权重给最低分：这是「没人被牺牲」的量化。方案卡上会写「最让步的是小林（0.74）」，而不是只说「匹配度 88%」。

② 两条独立的聚合规则，互相当裁判

规则它在回答什么怎么用
Borda 计数每个人心里的排名，加总谁更靠前排序
minimax regret最坏情况下，谁的后悔最小排序
一致度（Kendall τ）两种规则给出的排序有多像对外展示为「这个结果稳不稳」

示例局（5 人、下雨、6 小时）实测一致度 0.9351 —— 两种规则给出的顺序基本一致， 所以我们敢说「不是某一套规则凑出来的结论」。

③ 组合与动线：能枚举就别近似

候选池 24 个 → 2 个点的有序组合 552 种，3 个点的有序组合 12,144 种 → 共 12,696 种，全枚举 实测中位 86.8 ms（含读库与序列化）。这个规模用遗传算法是过度设计，答辩时可以直接说「枚举就够了，而且结果是全局最优」。

05三个真实 bug：从「用户说不对」到「修好并留下测试」

这一节最能说明项目是跑出来的，不是设计出来的。三个问题都是真实使用中撞到的。

bug 1 · 用户说「不想去室内」，系统却一直推荐室内

修之前
  • 解析器词表里没有「室内 / 商场 / 桌游」，这句话一个约束都没解析出来
  • 更糟的是「不想去室内，但如果下雨就算了」被读成 require_indoor = True（意思读反）
  • 就算解析对了也没用：字段是布尔，False 等于「没提这件事」，算法层完全无操作
修之后
  • 否定引擎：否定词前 6 字 / 后 6 字窗口 + 按标点分句 + 条件句单独处理
  • 字段从布尔改成三态 indoor_pref ∈ {-1, 0, +1}，两个方向都扣分
  • 实测：5 个人都说「想出去走走」→ 3 个方案9/9 个地点全是室外，且都带一顿饭
# 全员「想出去走走」的局（海岸城出发，6 小时，人均 ≤150）
方案 1  59.6%   文心公园 → 美食观光夜市 → 蛇口市场       全室外
方案 2  53.2%   深圳人才公园 → 华侨城创意文化园 → 车公庙美食街  全室外
方案 3  46.2%   荔秀天安夜市 → 深圳湾公园 → 东门老街       全室外

对应测试：test_saying_no_to_indoor_actually_changes_the_plans、test_wanting_to_go_outside_penalises_indoor_places。

bug 2 · 时间线把 22:43 排到一家 21:30 就打烊的书店

修之前
  • 算法不知道营业时间，第三个点经常落在打烊之后
  • 用户原话：「这个点人家早关门了」
修之后
  • 每个地点带 open_hour / close_hour，跨零点用 26.0 表示（夜宵摊到凌晨 2 点）
  • 按「到达时刻」判断，打烊的排列扣 25% 分而不是直接删掉
  • 实测：算法自己把顺序换了 —— 书店挪到 19:06，晚上 22:45 去吃火锅（23:00 关门）

对应测试：tests/test_hours.py 共 16 个用例，含 21 点出发时书店被标 closed、全天开放的公园永不误标。

bug 3 · 「海岸城到大鹏」被估算成 181 分钟，实际 85 分钟

商圈对（驾车）球面估算高德真实差
宝安中心 → 大鹏196 分97 分+99
海岸城 → 大鹏181 分85 分+97
大鹏 → 后海179 分85 分+94
190 对平均绝对偏差24.7 分—45.8% 的商圈对差 ≥20 分钟

深圳东西狭长 100+ 公里，用直线距离算时间会系统性地惩罚「东部景点」，导致推荐永远缩在西边。 所以用高德路径规划预计算了 190 对商圈的驾车/公交时间（380 次请求，落成一张 380 行的表）， 表里查不到的才退回估算 —— 运行时零 API 调用，断网也能跑。

表：data/area_travel.csv，跟着仓库走。对应测试：tests/test_travel.py。

三个 bug 的共同点：都不是「写错了语法」，而是模型的表达能力不够（布尔表达不了三态、地点没有营业时间、距离只有一个标量）。 修法都是先改数据模型，再加规则 —— 这也是一句话解析必须落在结构化字段上的原因。

07这一页的数字怎么重算

答辩现场如果要「证明一下」，按顺序敲这五条。

# 0. 装依赖 + 灌数据
pip install -r requirements.txt
python -m scripts.seed                  # → 共 202 条

# 1. 数据规模 / 分布 / 自检
python -m scripts.audit_pois            # → 0 处可疑

# 2. 125 个测试
python -m pytest -q                     # → 125 passed

# 3. 不开浏览器也能看到算法在干什么
python -m scripts.demo                  # → 三个方案 + 每人满意度 + 投票

# 4. 起服务，看真实延迟
python -m uvicorn app.main:app --app-dir backend --port 8000
curl -X POST localhost:8000/api/demo            # 拿示例局邀请码
curl -X POST localhost:8000/api/groups/<code>/recommend   # 三个方案 + 耗时
所有数字都是在本机（Windows / Python 3.12.14 / SQLite）实测的。 延迟在不同机器上会有差别，但量级不会变 —— 因为这个规模的枚举本来就是毫秒级。

08可能被问到的 10 个问题

每个答案控制在一口气能说完的长度。

为什么不让大模型直接推荐地点？
因为说不清「为什么是这家」。我们的取舍是：大模型（如果接）只负责把一句人话翻成结构化约束，排序仍然由可解释的效用函数算。 现在的规则版解析只要 3 毫秒、断网可用、每一条都能写成单元测试；接口留了开关，接不接都不影响主链路。
数据是不是从大众点评抄的？
不是。名字、坐标、评分、人均、营业时间来自高德开放平台的合法接口（有配额、有协议）； 室内外、安静度、人数、带娃、预约、排队、标签、一句话理由是人工标的。 data/pois_shenzhen.csv 就在仓库里，9 个人工字段一眼能看出来不是爬的。
这和大众点评的「附近推荐」差在哪？
它回答「这家店好不好」，我们回答「我们这群人今天该走哪条线」。 输出的是带时间的三段动线，而且会告诉你「谁让步最多」，这是点评类产品不会提供的信息。
为什么只做深圳？
这是刻意的取舍：十个城市各 20 条，不如一个城市 202 条标得准。 深圳还有三个特殊性正好喂算法 —— 东西狭长 100 公里（距离权重是核心）、暴雨台风多（室内外是硬约束）、按商圈活动（天然适合做动线）。 换城市要重跑四个脚本 + 人工复核，README 里写了步骤。
三个人想去 A，两个人想去 B，听谁的？
谁都不直接听。系统给每个人对每个地点打分，再用 0.6×平均 + 0.4×最低 聚合： 如果一个方案让两个人特别难受，最低分低，它排不上去。同时用 Borda 和 minimax regret 两套规则交叉验证， 两种排序一致度高才敢说结果稳。
怎么保证「公平」不是喊口号？
把它变成一个数：min(U) 占共识分的 40%。方案卡上直接写「最让步的是小林（0.74）」， 而不是只给一个「匹配度 88%」。让步者是谁可以拿去群里对质 —— 这是可验证的公平。
组合会爆炸吧？
这里不会。候选池 24 个，2～3 个地点的有序组合一共 12,696 种，全枚举只要几十毫秒（实测中位 86.8ms）。 用遗传算法反而是过度设计 —— 而且枚举能保证全局最优，答辩时更好讲。
断网能用吗？
能。地点表、商圈通行表、营业时间全部随仓库走，运行时零外部 API 调用。 只有「按日期查天气」会联网，查不到就退回手动选，建局不会失败。
一个人做的？怎么保证不是临时拼的？
看提交历史和 CI：从骨架到 202 条数据、从布尔到三态、从球面估算到 190 对路网表，都有对应的提交和测试。 每个功能都配了用例，改坏了 CI 会红。
商业上怎么走？
先不做商业化。真要做的话，最自然的入口是「群里那个负责组织的人」—— 他愿意为「不用挨个问」付时间成本。数据侧的优势是那 9 个人工字段，不是地点数量。
