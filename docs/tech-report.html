1项目与问题定位

1.1 它解决的到底是什么问题

真正的痛点不是「找不到好地方」，而是一群人凑不出一个决定。五个人的群聊里，每个人都能说出一个「不错的地方」， 但没人愿意替别人拍板；讨论四十分钟，最后往往去了楼下商场。推荐系统解决的是「一个人去哪」， 而这个问题里缺的东西恰恰是公平：不是平均分最高，而是别每次都让同一个人让步。

所以本项目的产品形态是三段：建局（拿到 6 位邀请码）→ 各填各的（三个滑杆 + 硬条件 + 一句话）→ 输出三个方案 + 投票定案。每个方案都同时给出「大家的共识度」和「谁让步最多」， 把群体决策里最容易被忽视的信息摆到台面上。

范围是刻意收窄的：只做深圳。一座城市的 202 个地点标得准，胜过十个城市各 20 条。 这个决定同时约束了数据、算法与文档——后面所有「为什么不做得更大」的问题，答案都回到这一句。

1.3 本文档的证据来源

三个问题分别对应三类证据，这也是本文档的组织方式：

  • 意图控制 → 证据是过程记录：需求原话、我给出的选项、最终选择、因此产生的提交。
  • 架构约束 → 证据是代码事实：依赖方向（algo/ 里 grep 不到任何框架名）、模块职责、迁移函数、降级分支。

2意图控制策略：怎么让 AI 做我要的东西

这一节回答的第一个问题是：AI 写代码时，「意图」到底在哪一层被决定？ 结论是：不在提示词里，而在约束里。提示词只能表达一次请求，约束才能让第二十次修改仍然朝着同一个方向。 所以我做的事可以概括成一句话——把意图从「话」变成「可以被检查的东西」。

2.1 从一句话需求到可执行约束

项目起点是一句很虚的话：「和朋友出去玩经常不知道去哪，需要一个软件综合各平台推荐，给出我们心目中的目的地」。 这句话里有三个陷阱：「综合各平台」（爬公开 API 拿不到的内容）、「我们」（多人，但没说怎么聚合）、「心目中的」（主观，无法验收）。 如果直接把这句话交给 AI，它会热情地开始写爬虫。

所以我先做的是三次收敛，每次都把一句模糊的话换成一个可检查的约束：

收敛原始说法换成可检查的约束理由
数据源 「综合各平台推荐」 只用高德开放平台的 POI 结构化字段；9 个拿不到的字段自己人工标注 大众点评无公开 API、小红书反爬严格。10 天里押爬虫，失败概率接近 1；而且合规风险不可控
范围 「出去玩」（全国？哪都行？） 只做深圳，20 个商圈，每商圈 8–13 个点 一个人 10 天能标准的只有一座城市；范围一收，数据质量、算法参数、文档都能收敛
验收 「给出心目中的目的地」 输出 3 个「地点组合 + 时间线」，每个都带共识度与「谁让步最多」 「心目中的」不可验收，「共识度 0.73、最让步的是小林（0.71）」可验收

同一套做法也用在了不做清单上。明确写进文档「不做」的东西，AI 就不会在实现时顺手加回来： 实时聊天、社交关注、微信授权、小程序（审核 3–7 天等不起）、多城市、支付、后台管理。 （其中“不做小程序”这一条后来证明是对的：传智杯提交窗口只有十天，审核时间直接吃掉三分之一。）

2.2 上下文分五层

「上下文」这个词，在我的用法里不是指「给 AI 贴多少代码」，而是五层逐级加严的约束载体。 越往下越难违反，因为违反了会立刻报错：

层载体约束什么违反了会怎样
L1README.md（项目宪法）做哪个城市、给谁用、砍掉什么、slogan、答辩口径人读一遍就能发现跑题，改回来成本最低
L2docs/ALGORITHM.md（公式）每个系数的值、每个惩罚的方向、为什么这样定义公平文档与代码不一致时，测试会红（测试注释直接引用章节号）
L3data/*.csv + algo/loader.py字段类型、枚举值、坐标范围、营业时间区间启动即抛异常，不允许脏数据进内存
L4backend/app/schemas.py请求/响应形状、取值范围（如 indoor_pref ∈ {-1,0,1}）422，并被压成人能看懂的文案
L5tests/ + CI行为契约：同一输入必须给同一输出CI 红，推不上去

五层里最有效的其实是 L3 和 L5，因为它们不依赖我记性。 举例：某次我让 AI 新增「品类偏好」字段，它很自然地想往 CATEGORIES 里塞一个新品类「书店」； 但 algo/types.py 里 7 个品类是封闭枚举，loader.py 会逐列校验， 于是它只能回头把「书店」映射到已有的「展览」—— 不是靠我提醒，是靠枚举挡住了。

2.3 四类提示词骨架

我给 AI 的请求从来不是「帮我实现 X」，而是四种骨架之一。骨架的价值在于：它把验收标准写进了请求本身。

骨架结构真实例子（节选）为什么有效
验收标准式 目标 + 可复现命令 + 期望 stdout + 不许破坏的既有行为 「把地点库扩到 150 条以上，要求：每个商圈至少 3 个室外点；python -m scripts.seed 要输出总条数；pytest 不许红；错标只改 CSV 一行就能修」 「至少 3 个室外点」是数字，能立刻检验；「错标改一行」决定了数据与代码必须解耦
诊断优先式 先分析、给选项、不要动代码；人拍板后再实现 「先不要急着修改代码，先分析问题出在哪然后告诉我」 避免「猜一个原因就打补丁」。本次诊断出三层原因，只改最上面一层会白干（详见 2.6）
降级要求式 主路径 + 「XX 挂了也必须能跑」 「天气接口两个源都挂时，建局不能失败，退回手动选」 强制 AI 写出 except 分支，而不是让整条链路依赖外部服务
数字核对式 让 AI 自己数、自己改，并列出改了什么 「把 README 里的行数、测试数、地点数与代码对齐，逐条报差异」 文档里的数字是最容易腐烂的部分；本次核对揪出 9 处偏差（见 5.4）
「降级要求式」是我从失败里学到的。早期让 AI 接高德接口，它写得很干净——直到我拿真 Key 一跑， 发现「关键词搜出来的 typecode 不可信」：搜「剧本杀」首条返回的是咖啡厅的 typecode。如果请求里没写「拿不到怎么办」，AI 默认假设「拿得到」。

2.4 四类典型失控与对策

三天里 AI 反复犯的是同一批错误，所以我把对策也做成了固定动作：

失控类型真实发生的一次我的固定对策
悄悄改需求 让它「修好室内偏好」，它顺手把「必须室内」做成了硬过滤（直接删掉所有室外点） 要求任何「过滤」都必须说明删掉了多少候选；默认只降权不删除，除非全组一致（见 3.x 全员排除规则）
只加常量不改公式 为了「别让方案只有 3 小时」，它加了 UNDERFILL_PENALTY = 0.15，但忘了把它乘进 score，白跑一次 之后所有评分改动必须给出同一输入改前/改后的方案对比；没有对比就当没改
编数字 README 里出现过「1 062 行算法被 47 个测试覆盖」，而当时实际是 1 319 行 / 69 个测试 所有规模数字必须附一句怎么数出来的；改完代码后强制重数（数字核对式提示）
假装完成 「已修复」但真实数据库里旧列还在，一写入就 500（preferences.require_indoor NOT NULL） 验收标准里必须包含在真实库、真实端口上跑一次，不接受「单元测试过了」

2.5 人机分工的边界

我把决策分成两类，并且只对第一类负责：

  • 不可逆 / 有代价的决策——人拍板。做哪个城市、用什么技术栈、砍掉哪些功能、要不要接大模型、要不要公网。 这些决策一旦错了，三天时间补不回来，所以我要求 AI 每次只给 2–3 个选项 + 各自代价，由我选。
  • 可逆 / 可验证的实现——AI 主导。具体算法实现、SQL 迁移写法、CSS 排版、测试用例。 这类东西错了有编译器和 CI 兜着。

举个真实的分歧：我问「能不能把那一栏接入 AI 让它真听懂人话」。AI 的回答是先否掉一半—— 「只接 AI 修不好这个 bug」：因为问题有三层（词表没有、字段是布尔只能表达「要室内」、数据里某个商圈 5 个点全是室内）， 大模型只解第一层。然后它给了我 A/B/C 三个方案与各自工时，我选了 C（纯规则增强）。 这个选择后来被验证是对的：规则版解析 3 毫秒、可写测试、断网可用，而且真正让「不想去室内」生效的是把布尔改成三态，不是语言模型。

2.6 诊断优先于修复：一次完整的三层排查

用户报的原始问题是：「我说不想去室内，但依旧给我推荐室内去的地方，甚至所有人都说不想去但依旧推荐」。 请求里我明确写了「先不要改代码」。AI 交回的诊断把问题拆成三层，每层都有可复现的证据：

层证据如果只修这一层会怎样
解析层 nlp.py 的室内词表只有「下雨 / 台风 / 太晒 / 高温」等天气词，没有「室内」这个词本身；实测 6 句话全部解析为「未提及」 补词表能听懂，但结果仍然一样——因为下一层不认
字段层 Preference.require_indoor 是布尔，只在为 True 时乘 0.2 惩罚；False 等于「没表态」 这是核心：布尔表达不了「我不想」，必须改成三态 indoor_pref ∈ {-1,0,+1} 并双向惩罚
数据层 49 个点里 26 个室内；而海岸城 5 个点全部室内，距离权重又是全表最高（0.30），「近的优先」必然导向室内 模型再对，池子里没有室外点也出不来室外方案

这次排查直接决定了后面三天的路线：改词表与否定引擎 → 改字段为三态 → 把数据从 49 条扩到 202 条。 如果当时直接按「加个 AI 就好」的思路动手，三层里只会修第一层，而这个 bug 至今还活着。

意图落成的约束可检查的结果

3架构设计：AI 生成的代码被约束成了什么形状

AI 写代码有一个稳定倾向：把所有东西塞进路由函数里，因为那样最短、最像「能跑」。 如果我只看结果不看结构，三天后会得到一个 800 行的 main.py——能演示，但没法测、没法改、没法答辩。 所以架构不是「设计出来的」，是用规则逼出来的。这一节讲清四层结构、每层被允许做什么，以及这些规则靠什么强制。

3.1 四层与依赖方向

      │  fetch /api/*
      ▼

      │
      ▼

      │
      ├──────────────► algo/   纯算法包（1 319 行，不 import 任何框架）
      │
      ▼
backend/app/models.py + db.py   ORM 与迁移（303 行）
      │
      ▼

依赖方向是单向的，这条规则可以用一行命令检查：

$ Select-String -Path algo\*.py -Pattern 'fastapi|sqlalchemy|starlette|pydantic'
# （无输出）—— 算法层不认识任何一个 Web / ORM 库

3.2 为什么算法层不认识框架

这不是洁癖，是三个具体收益：

  • 可测。40 个算法测试直接 import algo，不需要数据库、不需要 HTTP、不需要起服务，跑完 3 秒。
  • 可替换。如果哪天要换 FastAPI → Flask，或者 SQLite → PostgreSQL，algo/ 一行不用动。
  • 可解释。答辩时我能当场打开 algo/utility.py 指着公式说「这一项就是安静度的代价」，而不必在一堆 @app.post 里翻。

为了让这条边界在「AI 加功能」时不被冲垮，中间必须有一层唯一翻译层： backend/app/services/recommender.py 是整个项目里唯一同时认识 ORM 和 algo 的文件， 它只做三件事——把 POIRecord 转成 POI、把 PreferenceRecord 转成 Preference、调用一次 run_recommendation()。 换句话说：想绕过算法层直接写业务逻辑，AI 得先绕过这个文件，而它只有 112 行。

3.3 契约先行

「先定数据形状，再写逻辑」是我给 AI 的硬要求。项目里有三份契约：

契约载体校验方式违反时的表现
数据契约data/pois_shenzhen.csv 20 列algo/loader.py 逐列校验：品类必须在 7 个枚举内、经纬度在深圳范围内、营业时间 0 ≤ open < close ≤ 26启动即抛 ValueError，并指出是哪一行哪一列
接口契约backend/app/schemas.pyPydantic 模型 + 约束（indoor_pref: ge=-1, le=1）422，并被全局 handler 压成一句人话
行为契约tests/ 125 个用例同一输入必须同一输出（含时间线分钟数）CI 红，推不上去

契约先行带来的一个意外好处：字段可以先于数据库演化。 解析器最早就能输出 16 个字段，但数据库只有 11 列； 于是 merge_hints() 写成「if key in merged: 才写」—— 解析器可以先上线、先显示灰色提示，等表结构补齐后再自动生效。这让「加字段」从一次性大改变成了三次小改。

3.4 状态演化与迁移

SQLite 的 create_all() 只会建表，不会删列、不会改类型。项目里踩过两次：

  1. 补列：db.py 里有一张 _ADDED_COLUMNS 表，启动时用 PRAGMA table_info 比对，缺哪列补哪列（open_hour、start_hour、weather_text 都是这样加进来的）。
  2. 改语义：把 require_indoor（布尔）改成 indoor_pref（三态）时，老库还留着 require_indoor NOT NULL， 新插入不带它就 500：sqlite3.IntegrityError: NOT NULL constraint failed: preferences.require_indoor。 修法是 _drop_legacy_indoor_flag()：改名老表 → 重建新表 → INSERT ... SELECT ..., CASE WHEN require_indoor THEN 1 ELSE 0 END → 删老表。
这里有一次真实的失败，值得记下来：第一次跑迁移报 index ix_preferences_member_id already exists—— 因为 SQLite 的索引名是全库唯一的，把表改名后旧索引还在，新建表想用同名索引就撞了。 正确顺序是：先收集旧索引名 → 改名 → DROP INDEX → 建表 → 拷数据 → 删老表。 修好之后我造了一个老 schema 的库（含 require_indoor、唯一索引、两行数据）做回归，输出确认列已变成 indoor_pref、数据行数不变。

3.5 降级链

这个项目有四个外部依赖，每一个都可能挂。架构上要求：任何一个挂了，页面仍然能用，只是精度下降。

依赖失效表现降级动作用户看到什么
高德路网（商圈通行）表里查不到这对商圈 / 没网退回球面距离 + 地铁/驾车两套参数估算方案照常出，只是时间略粗；误差约 20%（最大例子：海岸城→龙华 估算 40、高德公交 83 分钟）
高德天气（4 天）接口超时换 Open-Meteo（7 天）；两个都挂 → 只影响「能选几天」建局不失败，日期选择器仍然可用，点查不到时提示「可以先手动选天气」
两个天气源都挂预报整表为空返回 in_range=true, kind=null页面显示「这天的预报暂时没查到」，不拦建局
邀请码生成重名冲突6 位码循环重试；成员重名按昵称幂等无感

降级链的设计原则是「坏消息要说清楚，但不许拦路」：能算就算，算不准就标注，绝不因为一个可选数据源不可用就把主流程打断。

3.6 复杂度预算

AI 很容易把「优化」当成「上算法」。这个项目的搜索空间其实很小，所以架构上明确写死：枚举，不上遗传算法。

阶段规模实测
单点打分202 个地点 × 5 人1 005 次打分
候选池共识分前 24（最多 +4 个餐饮兜底）—
组合枚举C(20,3) = 1 140 种组合 × 6 种顺序约 3 毫秒
多样性去重Jaccard 阈值 0.20 → 0.34 → 1.01 逐级放宽保证三个方案不共用前两个点

「这个规模枚举就够了」在答辩里是个加分项：它说明我知道什么时候不该上复杂算法， 而不是把遗传算法当勋章。同理，第 3.7 节的前端也不用框架——单文件 806 行，评委双击就能开。

3.7 前端策略

前端只做了一个决策：零构建。一个 web/index.html，内联 CSS 与 JS，不装 npm、不打包、不依赖 CDN。 代价是我得手写状态管理（一个 state 对象 + localStorage 两个键）；收益是：

  • 评委 clone 下来 只需要 Python，不必先跑 npm install（这一步在国内网络下经常卡十分钟）；
  • 静态页由 FastAPI 直接挂载，改前端不用重启服务（每次请求读磁盘）；
  • 整个产品只有 64 个被跟踪文件，最大的是两张截图（161 KB）。

3.8 约束怎么被强制

诚实地说：分层依赖没有被工具自动检查（Python 没有类似 Java 的模块依赖校验）。 它能保持，靠的是三件半自动的事：

  1. CI 的四道门：ruff check → python -m scripts.seed（数据契约）→ pytest（行为契约）→ 真起服务 curl /api/health 与 /api/areas（端到端）。
  2. 一行 grep：新增 algo/ 文件时，跑一次第 3.1 节那条命令，有输出就说明层被污染了。
  3. 文件大小直觉：recommender.py 112 行、routers/ 每个文件不到 350 行。某个文件突然变两倍，通常意味着职责混了。
  4. 文档里写明禁令：docs/ALGORITHM.md 开头就写着「本文档对应 algo/ 里的每一个函数」，AI 每次改算法都要顺手改这一节，改不动就说明改错了层。

同样重要的是「没做什么」。下面三条我都认真算过成本，也都在不同时间点上放弃了， 理由写在这里，因为答辩时它们比成功路径更容易被问到：

路线如果做了会怎样为什么放弃
让大模型直接推荐地点 十行代码就能出「听起来很美」的答案，演示效果立刻变好 ① 评委问「为什么是这家」时只能回答「模型说的」；② 断电断网即废； ③ 同样的输入不保证同样的输出，§4.3 的确定性论证整节作废
爬大众点评 / 小红书补「多平台」 数据量能翻十倍，也更像「综合各平台」 ① 都没有公开 API，反爬强度高；② 10 天窗口里失败概率接近 1； ③ 合规风险不可控——这一条足以让作品在合规审查上直接出局
做微信小程序 / 接微信登录 分享到群里更顺手，看起来更「完成」 ① 小程序审核 3–7 天，评审窗口只剩 10 天；② 授权要企业主体； ③ 同一套 H5 + 6 位邀请码已经能覆盖「发到群里大家各填各的」这个核心动作

这三条的共同点是：它们都能让演示更好看，但都会削弱「这东西为什么可信」。 在一个三天能跑起来的项目里，删掉一条路线省下的不是代码量，而是答辩时无法回答的问题。
