# 算法说明书

> 这份文档对应 `algo/` 里的每一个函数。文中所有公式都是代码里实际跑的，不是事后补的描述。
> 每个公式都有一条单元测试钉住（见 `tests/test_algo.py`）。

## 0. 问题形式化

给定：

- 一个地点池 `P = {p₁ … pₙ}`，每个地点有属性：品类、坐标、人均、评分、安静度、室内/室外、
  容量 `[min_people, max_people]`、是否适合带娃、排队程度；
- 一组参与者 `M = {m₁ … m_k}`，每人对三个维度有偏好：安静度 `q ∈ [0,1]`、
  消费意愿 `c ∈ [0,1]`、距离容忍 `d ∈ [0,1]`，另有硬约束（忌口、预算上限、想待室内还是想出去走走、带娃、开车）；
- 出发点 `o`、时间窗 `W`（分钟）、天气。

求：一个最多 3 个地点的有序序列 `S = (p₁, p₂, …)`，使**群体共识度最大**，
且满足品类不重复、含至少一个餐饮/咖啡、总耗时接近但不超出时间窗。

注意目标和约束的区别：这里优化的是"群体共识"，而不是"平均满意度"。见第 3 节。

## 1. 单人效用函数 `U(p, m) → [0,1]`

`algo/utility.py: score_poi`

```
U = 0.20·rating(p) + 0.18·quiet(p,m) + 0.20·price(p,m)
  + 0.30·dist(p,m) + 0.06·queue(p) + 0.06·kids(p,m)   ← 仅当 m 带娃时计入
```

权重之和为 1，因此基础分天然落在 `[0,1]`。各项定义：

### 1.1 评分 `rating(p)`

```
r̂ = clip((rating − 3.5) / 1.5, 0, 1)
```

3.5 分以下一律记 0。**理由**：深圳 POI 评分集中在 4.0~4.8，线性使用原始分会把
4.6 和 4.7 的差别放得比"能带娃 vs 不能带娃"还大，这是不对的。

### 1.2 安静度 `quiet(p,m)`

```
quiet = 1 − |quiet(p) − q(m)|
```

用"和用户理想值差多少"而不是"越安静越好"。喜欢热闹的人（`q=0.2`）
在安静的展馆里也会扣分——这是"一个人的推荐"容易忽略的细节。

### 1.3 价格 `price(p,m)`

先由消费意愿滑杆换算出心理价位：

```
ideal(c) = 40 + 260·c        # c=0 → 40 元（学生党）；c=1 → 300 元（舍得花）
```

然后：

```
price = 1                                    if avg_price ≤ ideal
      = clip(1 − (avg_price − ideal)/(1.5·ideal))   otherwise
```

**低于心理价位永远不扣分**，而不是"越便宜越好"。否则给一个舍得花钱的人推荐
人均 30 的店，会被算法认为"他很满意"，这在产品上是错的。

### 1.4 距离 `dist(p,m)`

```
minutes = travel_minutes(o, p)                     # 见第 2 节
half_life = 15 + 25·d(m)                           # d=0 → 15 分钟就掉一半分
dist = 0.5 ^ (minutes / half_life)
```

用**指数衰减**而不是线性：人对 10 分钟和 20 分钟的差别很敏感，对 70 分钟和 80 分钟几乎没感觉。
半数衰减时间跟着每个人的距离容忍度走——愿意跑远的人衰减慢，只想在楼下的人 15 分钟就开始心疼。

### 1.5 容量与排队

```
people_fit = 1                                        if min ≤ k ≤ max
           = clip(1 − (min − k)·0.25)                 if k < min（包间起订）
           = clip(1 − (k − max)·0.15)                 if k > max（坐不下）

queue = clip(1 − queue(p))
```

容量不足时额外扣分 `−0.10·(1 − people_fit)`。

### 1.6 硬约束：强惩罚而不是过滤

| 违反 | 处理 |
| --- | --- |
| 命中忌口标签 | `U ← 0.2·U` |
| 超预算上限 | `U ← 0.2·U` |
| 想待室内但地点在室外 | `U ← 0.2·U` |
| 想出去走走但地点在室内 | `U ← 0.2·U` |

**为什么用惩罚不用过滤**：如果五个人的约束交集为空（一个不吃辣、一个想待室内、一个预算 50），
过滤会让候选集直接变空，产品只能报错。惩罚能保证"最不坏"的方案始终存在，
并让解释卡可以诚实地说"这个方案让某某让步最多"。

`0.2` 这个数不是拍的：乘以 0.2 后，一个硬约束违例的地点必须在其所有其他维度上接近满分
（约 1.0/0.2 = 5 倍优势）才能反超一个合格地点。测试 `test_hard_penalty` 覆盖了这一点。

**室内这条为什么是三态而不是布尔**：第一版只有 `require_indoor: bool`，
结果"我今天不想去室内"这句话在算法里完全没声音——`False` 等于"没提这件事"。
于是改成 `indoor_pref ∈ {-1, 0, +1}`（想出去 / 无所谓 / 想待室内），两个方向对称惩罚。
这是这个项目里唯一一次"用户说了一句话、系统装没听见"的真实 bug，答辩可以直接讲。

### 1.7 候选池里为什么必须留几个吃的

`algo/combine.py: build_plans` 的规则是：一条动线里**品类不能重复**，且**必须含一顿饭**
（餐饮或咖啡）。这条规则本身没错，但它带来一个隐蔽的坑——

当五个人全都说"不想在室内"，室内餐饮会被 0.2 的惩罚压出共识分前 24 名，
于是候选池里一个"吃的"都没有，"必须含一顿饭"就把所有组合否掉了，
最终返回"偏好冲突太强，没有找到能凑成动线的组合"。

修法：取池子时**额外补最多 4 个共识分最高的餐饮/咖啡地点**（`pool_ids.append`），
池子从 24 变成最多 28；万一数据太少池子里仍然没有吃的，再退一步允许"没有饭的动线"。
测试 `test_everyone_wants_outdoors_still_gets_plans_with_food` 钉住了这个场景。

### 1.8 文字里的偏好：软加分，不是硬过滤

一句话里除了天气/安静/预算这类"滑杆级"信息，还有三类东西原先只能显示成灰色提示、
根本不进排序：**想去的品类**（"想吃火锅"）、**不想要的品类**（"不要玩桌游"）、
**想拍的照/想坐的座位**这类软愿望。现在它们各自有明确权重：

| 信号 | 处理 | 数值 |
| --- | --- | --- |
| 命中所想品类 | `parts["想去的品类"]` 加分 | `CATEGORY_BONUS = 0.07` |
| 命中所想要标签 | `parts["偏好标签"]` 加分 | `TAG_BONUS = 0.04` |
| 命中所排除的品类/标签 | `U ← 0.2·U` | `HARD_PENALTY` |

**为什么加分不硬选**：把"想吃火锅"做成只留火锅，一次误判就把整池子好地点毙掉——
规则解析本来就会漏读，代价不该由用户承担。加分的效果是"同一档里火锅排前面"，
在 202 个地点里已经足够把火锅推到方案首位（实测 `八合里潮汕鲜牛肉火锅` 直接进方案 1）。

**排除比"想去"更窄**：`excludes_poi()` 只有"词等于品类名"或"命中该地点的标签/名字"才判排除。
"不要玩桌游"不该把密室、剧本杀一起毙掉——它们同属"玩乐"但不是一件事。
反过来 `wants_poi()` 会先做别名映射（`火锅 → 餐饮`、`KTV → 夜生活`、`商场 → 玩乐`），
因为"想吃火锅"要落到整个餐饮品类上才有候选。

### 1.9 一个人的时长上限，和全组的出发时间

- **时长上限**（"最多三小时"）记在个人偏好里，`algo/combine.py` 取全组**最小**的
  `min(max_minutes)`，每条动线按超出比例扣分：`over_cap = 0.20 × (total - cap)/60`。
  用扣分而不是硬截断：这是他一个人的上限，别人还想玩，砍掉整条动线不公平。
  实测 "最多三小时" 下方案总时长是 184 分钟，贴着上限但没有爆掉。
- **出发时间**（"我七点才下班"）取全组**最晚**的 `start_hour`，写进 `Recommendation.start_minute`，
  随每个方案一起下发，前端 `fmtClock(offset, start_minute)` 渲染成 `19:03 → 20:35 → 22:43`。
  取最晚是因为人不能分身：早到的人可以等，晚到的人赶不上就是赶不上。

### 1.10 营业时间：到了门口得还开着

原先的排序完全不看营业时间，于是出现过「19 点出发、22:43 才到南山书城」这种方案——
分数很高，但到了门口已经关门。

现在每个地点带 `open_hour` / `close_hour` 两个数（`algo/types.py`），
`combine.py` 在算出每条动线的偏移量之后逐个检查：

```
closed = [p for i, p in enumerate(seq) if not p.is_open_at((start_minute + offsets[i]) / 60)]
score -= CLOSED_PENALTY · len(closed)          # CLOSED_PENALTY = 0.25
```

三个实现细节：

- **跨零点**：酒吧 `18:00-02:00` 存成 `(18.0, 26.0)`，`is_open_at(1.0)` 为真、`is_open_at(3.0)` 为假。
  如果按 `open < h < close` 直接判，凌晨营业的店会永远判成关门。
- **降权而非删除**：0.25 的惩罚足以让 21:30 关门的书店掉出首选，但只要把出发时间提前半小时
  就又能去——硬删会把「换个时间就行」的方案藏起来。
- **数据来源**：202 条里 149 条直接来自高德 `open_time`，其余按品类和名字兜底
  （见 `scripts/open_hours.py: default_hours`）。高德的串有 `09:30-22:00`、`08:30-11:30 13:30-17:00`、
  `24小时营业`、`18:00-02:00` 四种写法，中途休息的多段取包络。
- **前端**：`hours` 字段随方案下发，打烊的点圆点变黄、下面加一行「这个点到已经打烊了」。

实测效果：同一个局（19:00 出发）算法自己把顺序换成了
`南山书城 19:06（09:30-21:30）→ 太平洋影城 20:43 → 八合里火锅 22:45（11:00-23:00）`，
三个点全部还在营业时间内。测试 `test_a_place_that_closes_early_is_flagged_when_we_start_late` 钉住了这个行为。

## 2. 通行时间：预计算表 + 球面估算

分两层：**先查表，查不到才估**。

**第一层，表**（`algo/travel.py` + `data/area_travel.csv`）：
20 个商圈两两 190 对 × 驾车/公交 = 380 次高德路径规划，落成 380 行 CSV 跟着仓库走。
`pair_minutes(a, b, has_car)` 同商圈或查不到返回 `None`，交给第二层。

**第二层，估算**（`algo/geo.py: estimate_travel_minutes`）：

```
km = haversine(o, p)
km ≤ 1.2        →  分钟 = max(2, km/4.8·60)                     # 步行
有车            →  分钟 = km·1.25/24·60 + 8                     # 驾车含找车位
否则            →  分钟 = km·1.35/26·60 + 8                     # 地铁含进出站
```

**估算到底差多少**（实测四对，单位分钟）：

| 商圈对 | 驾车（真实） | 公交（真实） | 球面估算 | 偏差 |
| --- | --- | --- | --- | --- |
| 海岸城 → 大鹏 | 85 | 193 | 202 | −9 |
| 海岸城 → 龙华 | 47 | 83 | 40 | **+43** |
| 后海 → 万象城 | 35 | 56 | 69 | −13 |
| 宝安中心 → 盐田 | 70 | 132 | 135 | −4 |

偏差最大的是「海岸城 → 龙华」：估算 40 分钟，实际地铁 83 分钟——
因为两地直线不远，但中间隔着山和没直达的线。

**为什么不用直线距离**：深圳东西狭长，宝安到大鹏直线 60 km，实际地铁 2 小时。
直线距离会把"跨区"的成本严重低估。**为什么不全用实时路况**：见第 6 节。

## 3. 群体聚合：共识分

`algo/aggregate.py`

这是整个项目最核心的一行：

```
共识分 C(p) = 0.6 · mean_m U(p,m) + 0.4 · min_m U(p,m)
```

### 3.1 为什么不是纯平均

| 方案 | 甲 | 乙 | 丙 | 平均 | 共识分 |
| --- | --- | --- | --- | --- | --- |
| A | 0.9 | **0.1** | 0.9 | 0.633 | 0.420 |
| B | 0.7 | 0.6 | 0.6 | 0.633 | 0.620 |

平均分完全一样，但 A 里乙是去受罪的。共识分让 B 胜出——**这就是"一群人的决策"和
"一个人的推荐"的分界线**。测试 `test_consensus_rewards_fairness_over_raw_average` 钉住了这个例子。

`0.6 / 0.4` 的取值含义：可以理解为"整体体验重要，但别把任何一个人牺牲掉"。
把 0.4 调高会更偏向"人人及格"，调低会退回纯平均。我们在深圳数据上试过 0.5/0.5 到 0.7/0.3，
排序结果变化很小（说明结论稳健），最终选 0.6/0.4 是因为它在"有人极端不满"的场景下区分度最好。

### 3.2 两条独立的交叉验证

**Borda 计数**：每个人给所有地点按自己的 `U` 排名，第 1 名得 `n−1` 分，累加后按最大值归一。

```
borda(p) = Σ_m (n − 1 − rank_m(p)) / (k·(n−1))
```

只看相对名次、不看绝对分数，所以能抵抗"某个人打分特别宽松"的干扰。

**Minimax regret（最小最大后悔）**：

```
regret(p) = 1 − max_m ( max_{p'} U(p',m) − U(p,m) ) / 1
```

每个人先看"我本来最高能拿多少"，再看这个地点让他损失多少；取最大损失，
就是选它的最坏情况后悔程度。它对应的是"别让任何人特别后悔"这个决策心理。

**一致度**：Borda 排名与共识分排名的 Kendall tau（无并列版），

```
agreement = 一致对数 / 总对数 ∈ [0,1]
```

`agreement < 0.6` 时前端提示"这组偏好分歧明显，建议直接投票"。
三条路径结论一致，说明排序不是调参调出来的；不一致，说明这群人本来就没有共识，
此时算法不该假装自己有答案——**这个提示本身就是产品的一部分**。

## 4. 组合与动线搜索

`algo/combine.py: build_plans`

### 4.1 搜索空间

```
1) 剪枝：取共识分 Top 24 作为候选池
2) 枚举：C(24,2) + C(24,3) = 276 + 2024 = 2300 种组合
3) 每种组合最多试 3! = 6 种顺序（2 个地点时 2 种）
   总评估次数 ≈ 2024·6 + 276·2 ≈ 1.27 万
```

单次评估只做几次浮点加法和查表（两两通行时间预计算在字典里），
在普通笔记本上 **全程 < 50 ms**。

### 4.2 为什么穷举而不上遗传算法

这是答辩时最容易被问的问题，答案分三层：

1. **规模不够。** 1.27 万次评估，穷举是毫秒级的。遗传算法要跑种群迭代，
   时间不会更短，还多了一堆参数。
2. **穷举是全局最优的。** 在这个规模下，穷举给出的就是整个候选池里的最优解。
   用启发式算法，你得到的是"可能是最优"，却要承担"演示时两次结果不一样"的风险。
3. **可复现性是产品需求，不只是工程偏好。** 五个人对着屏幕投票，
   如果 A 刷新一次方案就变了，这个产品直接失去信任。测试
   `test_recommendation_is_deterministic` 把这条钉死了。

> 换句话说：**聪明的算法不如把问题定义对。** 这个项目的时间花在
> "公平怎么定义""没填偏好的人怎么处理""下雨天该改什么"上，而不是花在调种群大小上。

### 4.3 方案排序

```text
base     = mean_{p ∈ S} C(p)                     # 组合的平均共识分
route    = travel(o → s₁) + Σ travel(sᵢ → sᵢ₊₁)   # 总通行时间
dwell    = Σ 品类停留时长(sᵢ)                     # 咖啡 60 / 展览 90 / 餐饮 90 / 影院 120 …
total    = route + dwell
over     = max(0, total − W) / 120               # 超出时间窗，每 2 小时扣 1 分
shortfall= max(0, W − total) / W                 # 时间窗太空，按缺口的比例扣

score    = base − 0.10·(route/60) − over − 0.15·shortfall
```

时间窗是**软约束**：超出后每超 2 小时扣 1 分，而不是直接丢弃。
这和硬约束用惩罚是同一个设计原则——保证在苛刻条件下仍有方案，并如实解释代价。

**两头都要扣，这是实测逼出来的**：最初只惩罚超时，于是"打算玩 6 小时"的局
会得出一个 3.1 小时的两点方案——分数最高，但用户的真实需求是"下午到晚上都有安排"。
加上 `0.15·shortfall` 之后，同样输入的首选变成 5.1 小时的三点方案
（西贝莜面村 → 桌游吧 → CGV 影城）。这条有测试守着：`test_time_window_is_filled_but_not_overbooked`。

### 4.4 三个方案必须不一样

按分数排序后，用 Jaccard 相似度做贪心去重：

```
overlap = max_{已选方案} |S ∩ S'| / |S ∪ S'|
```

阈值依次放宽 `0.20 → 0.34 → 1.01`（最后一档等于不设限），保证在候选充足时三个方案
真的不同，在候选很少时也不至于凑不满。否则用户看到"三个方案都是同一个咖啡店开头"，
会觉得算法在敷衍。第一档压得很紧是有意的：**宁可放宽标准，也不让三个方案长得一样**。

### 4.5 解释卡是规则生成的，不是大模型写的

`_explain` 根据实际计算结果拼一句话：

> `%Arabica(万象天地) → 何香凝美术馆 → 潮汕牛肉火锅；全员满意度 0.61~0.78，
> 最让步的是 小王（0.61）；全程约 5.2 小时；全程室内，下雨也不怕。`

**为什么不用大模型**：解释必须 100% 忠于算法实际算的东西。大模型会写出
"解释说在室内但地点在室外"这种话，而评委只要抽查一条就能发现。
规则解释的代价是措辞单一，收益是**永远正确**——这个交换在比赛里是划算的。

### 4.6 时间线：偏移量是这样累加出来的

方案对外的价值有一半在"可执行"。所以每个地点除了名字，还带一个
`offset_minutes`（从出发算起第几分钟到达），前端据此渲染 `14:02 → 15:34 → 17:06`。

```text
clock = travel(o → s₁)                    # 第一站：路程
clock += DWELL[sᵢ] + travel(sᵢ → sᵢ₊₁)    # 之后每站：上一站待多久 + 路程
```

三个约束都有测试（`test_every_plan_carries_an_ascending_timeline`）：
偏移量个数与地点数一致、**严格递增**、第一站大于 0（过去本身要花时间）、
最后一站小于 `total_minutes`（因为还要算最后一段停留）。

时间线不是前端自己编的。否则一旦算法改了路线顺序，页面上的时刻表就会和真实动线脱节，
而这种不一致在演示时最难解释。

## 5. 一句话 → 约束

`backend/app/services/nlp.py: parse_constraints`

规则版，四类模式：

| 类别 | 例子 | 产出 |
| --- | --- | --- |
| 天气/室内 | 下雨、太晒、台风 | `indoor_pref = 1` |
| 氛围 | 安静、别太吵 / 热闹、嗨 | `quiet = 0.8 / 0.2` |
| 消费 | 省钱、学生党 / 不差钱 | `price = 0.2 / 0.85` |
| 距离 | 别走远、腿懒 / 愿意跑 | `near = 0.2 / 0.85` |
| 硬约束 | 带娃、开车、不吃辣、人均 100 | `with_kids` / `has_car` / `exclude_tags` / `max_price` |
| 想去的品类 | 想吃火锅、去玩密室、想逛商场 | `prefer_categories = ["火锅"]` |
| 不想要的品类 | 不要玩桌游、别去密室 | `exclude_categories = ["桌游"]` |
| 软愿望 | 想拍照、想坐着 | `prefer_tags = ["拍照"]` |
| 时长 | 最多三小时、别太久 | `max_minutes = 180` |
| 出发时间 | 七点才下班、晚上出发 | `start_hour = 19` |

两个关键规则（都有测试）：

1. **矛盾不猜。** "安静和热闹都行"同时命中两组关键词时，宁可不判断也不乱猜。
2. **手动优先。** 用户已经拖过的滑杆（不为 0.5）不会被解析结果覆盖。
   用户拖到 0.9 又被一句"要热闹"改回去，是最伤信任的交互。

**为什么不用大模型**：规则可测、3 毫秒返回、断网可用，而且失败模式是"漏识别"
（用户可以自己补滑杆）而不是"胡说八道"（用户会对整个产品失去信任）。
要接大模型，正确做法是让它输出同样的 `ParsedHints` 结构，规则版本做兜底与交叉校验，
而不是让它直接决定推荐结果。

## 6. 为什么预计算，而不是实时调高德路径 API

单次推荐里，`travel()` 被调用的次数约为：

```
打分阶段：k 人 × n 地点        ≈ 5 × 202 = 1 010 次
组合阶段：预计算两两时间          ≈ 24²   = 576 次
```

一次演示要跑 3~5 遍，就是数千次调用。高德个人开发者配额是每天 5000 次、
QPS 有上限——**一次答辩就把配额打光**，而且网络抖动会让演示当场失败。

因此设计为：

1. 离线用高德路径规划 API 预计算「商圈 × 商圈」的两两时间
   （20 商圈 = 190 对 × 驾车/公交 = 380 次请求，双向各写一行，230 秒左右跑完），
   存成 `data/area_travel.csv`；
2. 运行时查表，表里没有的组合退回第 2 节的本地估算；
3. 这个取舍可以正面回答"你为什么不算得更准"：**准确度和可用性之间，
   演示当天可用性优先**；同时给出了升级路径（换表即可，算法层无改动）。

## 7. 复杂度小结

| 步骤 | 复杂度 | 实测（202 地点 / 5 人） |
| --- | --- | --- |
| 打分矩阵 | O(k·n) | ~1 ms |
| 聚合（含 Borda/regret） | O(k·n log n) | ~1 ms |
| 组合搜索 | O(C(P,3)·6) | ~30 ms |
| 合计 | — | **< 50 ms** |

这也是"为什么不需要缓存推荐结果"的依据：算一次比读一次缓存还快，
而实时计算能保证用户改完滑杆立刻看到新结果。
